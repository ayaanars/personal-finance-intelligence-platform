# ADR 0002: Initial database ownership foundation

Status: Accepted for the explicitly requested initial database foundation, 2026-09-07.

## Context

DATABASE.md and SECURITY.md specify one private workspace per user and composite
ownership foreign keys. The user authorized only the initial database foundation,
not authentication or financial features, and requested PostgreSQL verification.

## Decision

Implement only users and workspaces. Preserve the empty 0001 baseline and add
0002_identity_ownership. Credentials, sessions and audit records arrive with the
complete authentication design; financial tables arrive with their own features.

Use native PostgreSQL UUIDs generated by gen_random_uuid() at insertion (UUID v4),
including direct SQL inserts. Explicit UUIDs are supported for controlled callers.
Use TIMESTAMPTZ with statement_timestamp() defaults and UTC database connections.
A database trigger advances users.updated_at on every UPDATE, including direct SQL;
created_at is an insertion timestamp, not an enforced immutable audit record.
Callers must supply aware instants; PostgreSQL preserves the instant, not the original
zone label. Explicit source offsets belong in future source-provenance fields.

Require explicit user status, limited to DATABASE.md's four states. Do not define
status transitions or authentication behavior here. Store bounded display email and
an explicitly supplied normalized email. Enforce nonempty, lowercase, space-trimmed
normalized values and exact uniqueness; do not silently canonicalize input. Do not
strip provider aliases/dots or implement Unicode/IDNA email normalization. Email
syntax, internationalization and canonicalization at the input boundary must be
finalized and tested with authentication before any registration is exposed.

A unique owner_user_id permits at most one workspace per user. Registration must
later create both records atomically to ensure exactly one for each registered user.
The restricted users FK prevents orphan workspaces or cascading owner deletion.
UNIQUE (owner_user_id, id) is deliberately retained in addition to the owner unique
key as the exact target of future FOREIGN KEY (user_id, workspace_id) relations.
Primary/unique constraints supply all initial indexes; no speculative indexes.

Defer RLS for this foundation: the current architecture does not require it for MVP.
Composite ownership keys prevent mismatched relationships, but do not authorize
reads/writes. Future private repositories must require verified owner context and
owner predicates with cross-user tests. No private resource API ships here. Revisit
RLS and establish separate least-privilege runtime/migration roles before deployment;
the existing Docker owner credential is development-only.

No money columns or money helper types are needed. NUMERIC(20,4), Decimal and explicit
currency remain the financial design baseline. Supported currencies, over-scale input
rejection and rounding must be resolved before financial persistence is implemented.

## Alternatives

- Implement every proposed table: rejected because it fixes unapproved later-feature
  semantics and creates unused schema.
- Users alone: omits the already designed ownership boundary for subsequent accounts.
- RLS now: adds principal/session and pooled-connection policy ahead of authentication.
- ORM-only updated_at: fails to cover direct SQL changes.

## Consequences and verification

Models are persistence mappings, not authenticated repositories or domain services.
Alembic registers them explicitly and compares server defaults as well as columns.
Trigger/function behavior is tested separately because Alembic drift detection does
not inspect these objects or check-constraint expressions automatically.

PostgreSQL integration tests migrate a unique disposable schema per test in an
explicit test database. They verify creation, UUIDs, timezone instants, update
triggers, checks, uniqueness, restricted deletion and a cross-owner child FK probe.
Migration tests cover empty/baseline upgrade, downgrade, re-upgrade and a single head.
Downgrade drops these tables and their contents; use only on disposable data. For a
populated environment back up first and prefer a reviewed roll-forward migration.
